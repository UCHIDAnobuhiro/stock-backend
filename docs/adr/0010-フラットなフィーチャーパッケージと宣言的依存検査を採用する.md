# ADR-0010: フラットなフィーチャーパッケージと宣言的依存検査を採用する

| 項目       | 内容       |
| ---------- | ---------- |
| ステータス | Proposed   |
| 日付       | 2026-08-21 |

---

## コンテキスト

ADR-0002では、フィーチャーベースの垂直スライスを採用し、各フィーチャー内を
`domain`、`usecase`、`adapters`、`transport` のディレクトリに分割する方針を定めた。
その後、実装と運用を進める中で、Goでは小規模な責務ごとのディレクトリ分割が
パッケージ間の変換・import・命名を増やし、フィーチャー全体の理解を難しくすることが分かった。

また、依存制約を `depguard` の禁止リストで表現すると、許可していない新しい内部依存を
既定で拒否できない。OpenAPI生成型をフィーチャーコアへ持ち込まない境界や、
フィーチャー間の直接依存禁止を宣言的に検証する仕組みが必要になった。

## 決定

フィーチャーベースの垂直スライスは維持しつつ、各フィーチャーのドメインモデル、
ユースケース、リポジトリ実装を `internal/feature/<name>` の単一コアパッケージへ集約する。
レイヤーはディレクトリではなくファイルで分け、HTTP層、生成コード、外部APIアダプターだけを
別パッケージにする。

- HTTP層は `<name>http` に分離し、`internal/api` のOpenAPI生成型への依存をここへ閉じ込める
- sqlc生成コードは `sqlc`、外部APIアダプターは `twelvedata`、`gemini`、`vision` などの子パッケージに置く
- inbound HTTP共通処理は `internal/transport`、技術基盤は `internal/infra`、ドメイン横断の共有処理は `internal/shared` に置く
- DI・ルーティング・バッチ構成は `internal/app`、実行エントリーポイントは `cmd/api`、`cmd/batch`、`cmd/migrate` に置く
- リポジトリ等のインターフェースは利用者側のファイルで定義する
- `api/openapi.yaml` をHTTP契約の単一ソースとし、生成型の利用と実行時リクエスト検証をHTTP境界に限定する
- `.go-arch-lint.yml` で内部依存をデフォルト拒否し、許可する依存だけを列挙する
- `depguard` はアーキテクチャ境界ではなく、GORM再混入禁止など特定ライブラリの禁止に限定する

## 理由

**Goのパッケージ慣例との整合**
同じフィーチャーの密接な型と処理を単一パッケージへ集めることで、機械的な層分割のための
変換コードとimportを減らし、ファイルを上から追うだけで機能を理解しやすくなる。

**境界が必要な依存だけを分離**
HTTP生成型、生成DBコード、外部サービスSDKは変更理由が異なるため別パッケージに保つ。
フィーチャーコアはこれらの詳細から独立したインターフェースを所有する。

**デフォルト拒否による機械的な強制**
go-arch-lintで許可依存を列挙することで、設定にない内部依存を自動的に拒否できる。
フィーチャー分離、OpenAPI型境界、transport/infraからfeatureへの逆依存禁止をCIで検証できる。

**HTTP契約の一元化**
OpenAPIを生成型と実行時検証の両方に使用することで、仕様・受信検証・レスポンス型の
ドリフトを減らせる。multipartなど共通検証に適さない入力はハンドラーで明示的に検証する。

## 代替案

| 代替案 | 不採用の理由 |
| ------ | ------------ |
| ADR-0002の階層ディレクトリを維持する | Goパッケージが細分化され、同一フィーチャー内の変換・import・命名が増える |
| 全コードをフィーチャー直下の単一パッケージにする | HTTP型、生成コード、外部SDKの依存までコアへ流入し、変更理由の異なる境界が失われる |
| depguardだけで内部依存を管理する | 禁止対象の列挙が中心となり、未宣言の内部依存をデフォルト拒否できない |
| 依存ルールをレビューだけで運用する | 違反検出がレビュアーの知識と注意力に依存し、継続的な保証にならない |

## 影響

### ポジティブな影響

- フィーチャー内の関連コードを少ないパッケージ移動で読める
- フィーチャー間の直接依存と、コアからHTTP型への依存をCIで拒否できる
- transport、infra、sharedの責務と依存方向が明確になる
- 新しい内部依存は `.go-arch-lint.yml` への明示的な追加とレビューが必要になる
- OpenAPI仕様、生成型、実行時検証の対応関係を追跡しやすくなる

### ネガティブな影響・トレードオフ

- 単一コアパッケージのファイル数が増えるため、ファイル命名とトップダウン整列を守る必要がある
- 新フィーチャーやアダプター追加時に `.go-arch-lint.yml` のcomponents/deps更新が必要になる
- go-arch-lintはimport依存を検査するものであり、実行時のDI誤りやビジネスルール違反は検出できない
- テストファイルは白箱・黒箱双方の依存を許容するため、アーキテクチャ検査の対象外とする
