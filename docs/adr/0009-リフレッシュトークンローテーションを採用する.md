# ADR-0009: リフレッシュトークンローテーションを採用する

| 項目       | 内容       |
| ---------- | ---------- |
| ステータス | Proposed   |
| 日付       | 2026-08-04 |

---

## コンテキスト

従来の認証では有効期限1時間のJWTのみを発行しており、期限切れ後は再ログインが必要だった。
ブラウザ利用時の利便性を改善しつつ、長期間有効な認証情報の漏洩リスクを抑える必要がある。

本システムはCookie認証、OAuthログイン、CSRF保護、JWTブラックリストを既に採用している。
また、認証セッションはRedisの一時的な可用性に左右されず、再起動後も維持する必要がある。

## 決定

アクセストークンには有効期限10分のJWTを使用し、リフレッシュトークンには有効期限30日の不透明なランダム値を使用する。
リフレッシュトークンのSHA-256ハッシュをPostgreSQLへ保存し、使用ごとにローテーションする。
使用済みトークンの再利用を検知した場合は、同じ`family_id`に属するセッションをすべて失効させる。

## 理由

アクセストークンを短命化することで、JWT漏洩時の有効期間を制限できる。
リフレッシュトークンをサーバー管理することで、ログアウトや盗難検知時に即時失効できる。

不透明なランダム値を使用することで、リフレッシュトークン自体にユーザー情報を含めず、署名鍵とも分離できる。
DBにはハッシュだけを保存するため、データベースが漏洩しても保存値をそのまま認証へ利用できない。

PostgreSQLは既存の永続化基盤であり、トランザクションと行ロックを利用してトークン交換を一度だけ成功させられる。
Redis障害や再起動によって全ユーザーのログイン状態が失われることも避けられる。

## 代替案

| 代替案 | 不採用の理由 |
| ------ | ------------ |
| リフレッシュトークンにもJWTを使用する | サーバー側での個別失効や再利用検知に結局状態管理が必要になり、JWTである利点が小さい |
| Redisへ保存する | Redis障害やデータ消失時に全セッションが失われる可能性がある |
| 固定リフレッシュトークンを有効期限まで再利用する | 盗難後も攻撃者が繰り返しアクセストークンを発行できる |
| アクセストークンを長寿命のまま維持する | JWT漏洩時の被害期間が長くなる |

## 影響

### ポジティブな影響

- アクセストークン漏洩時の被害期間が10分に制限される
- ユーザーは30日間、再ログインせずセッションを更新できる
- ログアウト時にリフレッシュセッションを即時失効できる
- 使用済みトークンの再利用から盗難を検知できる
- DB上に平文のリフレッシュトークンを残さない

### ネガティブな影響・トレードオフ

- 認証更新ごとにPostgreSQLアクセスが発生する
- 同時に複数の更新要求が送信された場合、一方だけが成功する
- フロントエンド側で更新要求を単一化する必要がある
- 期限切れセッションを定期削除する運用が必要になる
- PostgreSQL障害中はトークン更新と完全なログアウトが利用できない
