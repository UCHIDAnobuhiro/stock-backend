---

振る舞いと回帰リスクを検証するテストを、既存のテスト構成に合わせて追加・更新する。

## 対象と方針

- 引数または会話で指定されたファイル・機能を優先する。指定がなければ `git status --short`、未ステージ・ステージ済み差分、未追跡のGoファイルから対象を特定する。
- 対象コードと同パッケージ・関連パッケージのテストを読み、既存ヘルパー・モック・`TestMain` を確認する。関数数や同名のテストファイルの有無だけで未検証と判断しない。
- 検証する振る舞い、正常系・異常系・必要な境界条件を簡潔に伝えて実装する。期待動作が不明な場合だけ確認し、テスト作成依頼に対する承認を再度求めない。
- 生成コードの直接テストや実装をなぞるだけのassertより、公開動作・契約と不具合の再発防止を優先する。

## 構成とスタイル

- 類似ケースはテーブル駆動の `t.Run` でまとめる。セットアップや検証が大きく異なるケースは別テストにできる。
- 同一パッケージの白箱テストと `<name>_test` の外部テストは、既存構成と検証対象に合わせる。HTTP層には外部テストもあるため、同一パッケージを強制しない。
- `t.Parallel()` はケースごとのDB・モック・状態が分離されている場合に使う。`t.Setenv`、共有DB・共有カウンタ・グローバル状態を変更するテストやその親を無条件に並列化しない。
- 関数型フィールドのモックと既存ヘルパーを再利用する。想定外の呼び出しを検出すべき場合は、未設定時に成功値を返して隠さない。呼び出し回数や引数の検証は契約上必要なものに絞る。
- 並行呼び出しを受けるモックの可変状態は同期する。サブテスト内のassertはそのサブテストの `t` を使い、別goroutineから `require` / `t.Fatal` を呼ばない。
- `assert` / `require` は既存利用に合わせる。先にセットアップとエラーを `require` で確認し、戻り値を検証する。新規ヘルパーには `t.Helper()`、後片付けには `t.Cleanup()` を使う。
- テスト名は `Test<型名>_<メソッド名>` 等の既存形式に合わせ、ケース名は意図の分かる英語にする。コメントは既存の日本語・英語の文脈に合わせる。

## 層ごとの検証

| 対象 | 手法 |
| --- | --- |
| usecase / バッチ | 利用者側インターフェースのモックで業務ルール・エラー伝播を検証 |
| HTTP handler | `net/http/httptest` と必要に応じたchiルーター。usecaseをモックしステータス・JSON・Cookie等を検証 |
| ルーター / middleware | 実際のmiddleware構成で認証・CSRF・OpenAPI検証の順序や契約を検証 |
| PostgreSQL repository | `internal/infra/db/dbtest` の `RunMainWithPostgres` / `OpenIsolatedDB` 等、既存の実DBヘルパーを使用 |
| 外部HTTPアダプタ | `httptest.Server` 等で応答・失敗・キャンセルを再現し、外部APIへ実リクエストしない |
| Redis / 共通基盤 | 既存の `redismock`・`miniredis` 等を目的に合わせて選び、再現できない実Redis固有の動作を検証済みと扱わない |

PostgreSQLテストはtestcontainersまたは `TEST_DB_DSN` を使用する。SQLiteではPostgreSQL固有SQL・制約・ロックを検証できないため代替しない。既存の `TestMain` があるパッケージでは、`-run` でunit testだけを選んでもDB起動が必要な場合がある。

## 実行と完了

1. 対象のテストファイルを `gofmt` し、対象パッケージを `go test ./<対象パッケージ>/... -v -race` で検証する。
2. 失敗時はテストの不備、実装の不具合、環境要因を区別する。期待値を誤動作へ合わせない。テスト作成だけの依頼で本体の修正が必要になった場合は根拠を報告し、修正も依頼済みならその範囲で進める。
3. 既存テストの意味を保ち、必要なヘルパー更新・重複整理を行う。追加位置を末尾だけに固定しない。
4. 追加した検証内容と結果、未実施の理由を報告する。環境不足を黙ってskipして成功扱いにしない。
