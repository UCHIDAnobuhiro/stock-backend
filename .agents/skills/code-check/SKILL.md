依頼対象の差分を読み、修正すべき具体的な問題を日本語で報告する。レビュー依頼だけではコードを変更しない。修正も依頼されている場合は、レビュー後にその依頼範囲で対応する。

## 対象を確定する

- 指定ファイルや比較範囲があれば優先する。指定がなければ `git status --short`、`git diff`、`git diff --cached`、`git ls-files --others --exclude-standard` で把握する。
- 未追跡の新規実装は通常のdiffに出ないため、対象の内容も読む。別作業のファイルを勝手にレビュー範囲へ混ぜない。
- コミット前は実際にコミットする差分を中心とし、未ステージの修正に依存していないかも確認する。PRレビューから呼ばれた場合は、呼び出し元が指定するbase/headを使う。
- 差分だけで断定せず、呼び出し元、API契約、生成元、既存テストを必要な範囲で追う。

## レビュー観点

- **責務・依存**: `AGENTS.md` と `.go-arch-lint.yml` に従う。コアとAPI型の境界、他フィーチャーへの依存、HTTP固有処理、利用者側のインターフェース定義を確認する。
- **動作**: 正常系・異常系・境界条件で契約を満たすか。認証・認可、入力検証、トランザクション、並行処理、context伝播、リソース解放、エラー処理を変更内容に応じて確認する。
- **生成物**: OpenAPI・SQL・migrationの変更と対応する生成物・スキーマ文書が整合しているか。生成物の不具合は生成元まで追う。
- **テスト**: 変更した振る舞いと回帰リスクを検証できているか。並列テスト間のDB・モック・環境変数の共有や、実装をなぞるだけの検証になっていないか。
- **読みやすさ**: 既存の命名・関数順序・責務の分け方と整合しているか。`candles` などの既存パッケージ名を単数形へ強制しない。行数・引数数・`-er` 接尾辞だけを根拠に問題としない。

Goの依存変更なら `go tool go-arch-lint check`、動作変更なら対象テストなど、変更に合う検証を選ぶ。文書のみの変更にGoのテストやlintを強制しない。検証を実施していない場合は理由を明示する。

## 結果

- 修正が必要な問題を重大度順に、ファイル・行、発生条件、影響、根拠、修正方向とともに示す。
- この差分が導入・悪化させた問題と既存問題を区別する。好みだけのスタイル提案や推測を要修正事項にしない。
- 指摘がなければその旨を明記し、確認範囲と検証結果・未実施事項を簡潔に添える。調査できない場合は問題なしと断定しない。
